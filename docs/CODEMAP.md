## 1. Stack & Conventions

Node ≥ 20 / Express 5, CommonJS (`require`/`module.exports`), plain JavaScript, function-based modules, async/await throughout. **No TypeScript remains** (verified: no `.ts`/`.d.ts` files, no `tsconfig`, no `ts-node` or `@types/*` in `package.json`).
Prisma 6 + PostgreSQL (Neon). Zod v4 for runtime validation. bcrypt for passwords. pino + pino-http for structured logging.
Runtime deps (`package.json`): `@prisma/client`, `@vercel/blob`, `bcrypt`, `cors`, `dotenv`, `express`, `express-rate-limit`, `helmet`, `jsonwebtoken`, `nodemailer`, `pino`, `pino-http`, `zod`. Dev deps: `jest` 30, `supertest`, `eslint` 10 (flat config) + `@eslint/js` + `eslint-config-prettier` + `globals`, `prettier`, `nodemon`, `pino-pretty`, `prisma`, `exceljs` (seed only). `multer` is **not** installed (removed after the client-upload refactor). Node `crypto` is used for UUIDs, refresh tokens, temp passwords and SHA-256 hashing.
npm scripts: `test` (`jest --runInBand`), `dev` (`nodemon src/server.js`), `start` (`node src/server.js`), `lint` (`eslint .`), `lint:fix`, `format` (`prettier --write .`), `prisma:generate`, `prisma:migrate` (`prisma migrate dev`), `prisma:seed` (`node prisma/seed.js`, owner seed), `seed:membership-plans` (`node prisma/seeds/membership-plans.seed.js`). On Windows use `npx.cmd`.
All env vars are validated at startup via Zod in `src/config/env.js`; the process exits on invalid config.
All user-facing validation/error text lives in `src/constants/messages.js` (one constant per distinct message, no duplicate texts); `auth.validation.js` has no inline message literals.
**Layout (layer-based MVC, since 2026-10-10):** `src/modules/` no longer exists. Files live by layer: `controllers/` (HTTP handlers), `services/` (business logic + `auth.guards`, `login.policies`, `staff.policies`), `repositories/` (Prisma data access + `user.mapper`, `staff.mapper`, `membershipPlan.mapper`), `validators/` (Zod schemas, `*.validation.js`), `routes/` (all route files incl. `auth/staff/uploads.routes.js`). File names are unchanged; the §3 headings below group rows by feature but every path is the real current path.
Patterns in use: Strategy (`login.policies`, `staff.policies`, `coach.access` role rules and `UPDATE_FIELDS_BY_ROLE`, all `Map`-based or frozen tables, deny by default), Chain of Responsibility (`auth.guards`), thin controllers, repositories as the only Prisma callers (plus `prisma.$transaction` in `staff.service`).
See [docs/ONBOARDING.md](./ONBOARDING.md) for full architectural rationale and decisions (`README.md` only contains the title "Backend").

## 2. Request Flow

```
HTTP → helmet → cors (origin allow-list) → clientType (sets req.clientType) → pino-http (logs clientType) → express.json (1mb) → express.urlencoded → route
     → authLimiter (auth routes) → validateBody(schema) → controller → service → repository → Prisma
                                                                        ↓ throw / next(err)
                                                        errorHandler (4-arg Express middleware)
Unmatched routes → notFound → errorHandler
```

Login flow detail (`POST /api/v1/auth/login`): see §9 "Implemented login flow".

Staff creation flow (`POST /api/v1/admin/staff`): `authenticate` (Bearer JWT, DB role/status) → `authorize(ADMIN, OWNER)` → `validateCreateStaff` → `staff.controller.createStaff` → `staff.service.createStaff` → repositories. Not behind `authLimiter`. Response 201 `{ success, message: STAFF_CREATED_SUCCESS, data: { ...staffUser, emailSent } }`; `tempPassword` is never in the response.

Coach flows: `POST /api/v1/admin/staff/coaches`: `authenticate` → `authorize(ADMIN, OWNER)` → `validateCreateCoach` → `staff.controller.createCoach` → `staff.service.createCoach` → shared `registerStaffUser` (role policy, duplicate-email check = 409 `COACH_EMAIL_ALREADY_EXISTS`, temp password, ONE transaction: User + Coach + `STAFF_CREATED` audit, post-commit invitation email). Response 201 `{ success, message: COACH_CREATED_SUCCESS, data: { ...fullCoachView, emailSent } }`. Reads and updates under `/api/v1/coaches`: `authenticate` → `authorize(roles)` → per-role validation (`validateByRole`: query or body schema chosen from `req.user.role`) → `coach.controller` → `coach.service` (ownership, visibility, editable fields via `coach.access`) → `coach.repository`. Query is validated into `req.validatedQuery` (Express 5 `req.query` is read-only).

Plan list flow (`GET /api/v1/plans`): `authenticate` → `authorize(OWNER, ADMIN, COACH)` → `planReadLimiter` → `validateListPlansQuery` (Zod, 422, unknown params stripped, result on `req.validatedQuery`) → `plan.controller.listPlans` → `plan.service.listPlans` (list query and the independent `meta.counts` query run in parallel via `Promise.all`; rows go through `toMembershipPlanResponse` then `pick(PLAN_LIST_ITEM_FIELDS)`) → `membershipPlan.repository` (`buildListWhere` + `listByColumn` or `listByNameOrder`, `countNonArchivedByCreditType`). Response 200 `{ success, data, meta }`.

Plan detail and edit flows: `GET /api/v1/plans/:id`: `authenticate` → `authorize(OWNER, ADMIN, COACH)` → `planReadLimiter` → `loadPlan()` (404) → `plan.controller.getPlan` → `plan.service.getPlan`. `PATCH /api/v1/plans/:id`: `authenticate` → `authorize(OWNER, ADMIN)` → `planLimiter` → `loadPlan({ rejectArchived: true })` (404, 409 `plan_archived`) → `validateUpdatePlanBody` (422; sets `req.validatedBody`) → `plan.controller.updatePlan` → `plan.service.updatePlan` (diff, `duplicate_name`, `plan_in_use`) → `updatePlanWithAudit` (one transaction; DB trigger bumps the version). `PATCH /api/v1/plans/:id/status`: `authenticate` → `authorize(OWNER, ADMIN)` → `planLimiter` → `loadPlan()` → `validatePlanStatusBody` (422) → `plan.controller.changePlanStatus` → `plan.service.changePlanStatus` (same-status shortcut, `PLAN_STATUS_TRANSITIONS`, restore-time name check) → `changePlanStatusWithAudit` (one transaction, compare-and-set on the old status). `router.all` after the real routes answers 405 + `Allow` for every other method on `/:id` and `/:id/status`.

## 10. Auth, Security & Cross-Cutting Summary

**Auth flow (where each piece lives)**

- Password hashing: `password.util.js` (bcrypt, `BCRYPT_SALT_ROUNDS`, default 12); password policy `PASSWORD_REGEX` (8+ chars with upper, lower, digit; max 72 enforced in schemas).
- Access token: `jwt.util.js` (HS256, `{ sub, email, role, type: 'access' }`, `JWT_ACCESS_EXPIRES_IN`; the email claim is informational, `authenticate` ignores it and re-reads role/status from the DB), issued in `auth.service.startLoginSession`, verified in `authenticate.middleware.js`, which re-reads role/status from the DB (`findAuthById`) and ignores the token's role claim.
- Refresh session: `token.util.js` (opaque token, SHA-256 hash), stored by `session.repository.createLoginSessionTx` in `RefreshSession` (hash only, ip, user agent, `expiresAt`). The repository functions for lookup/revoke/rotate (`session.repository`) are used by `refreshTokens` and `logout` in `auth.service.js`, exposed as `POST /api/v1/auth/refresh` and `/logout`; there is no endpoint to list or revoke sessions of another user.
- Authorization: `authorize.middleware.js` (role allow-list, throws on unknown role, logs every 403 with role/method/URL/IP/clientType/timestamp) + `staff.policies.js` (who may create which role: MEMBER/COACH own role only, ADMIN → ADMIN/COACH/MEMBER, OWNER → all four). The role always comes from the DB user loaded by `authenticate` (token `sub` only); header/query/body roles are ignored (tested). Coach routes add ownership and visibility rules inside `coach.service` (see §12).
- Audit logging: `audit-log.repository.js` (`createAuditLog`, `recordLoginFailure`); actions (9, as in `constants/audit.js` and the schema enum) `LOGIN_SUCCESS`, `LOGIN_FAILED`, `STAFF_CREATED`, `STAFF_CREATE_DENIED`, `PASSWORD_RESET_REQUESTED`, `PASSWORD_RESET_OTP_VERIFIED`, `PASSWORD_RESET_OTP_FAILED`, `PASSWORD_RESET_COMPLETED`, `LOGOUT` (written by `revokeSessionWithLogoutAuditTx` in the revoke transaction, only when a session was actually revoked; fields: userId, email, ip, user agent). Login audit writes are best-effort (never change the response); staff audit rows are written inside the creation transaction.
- Staff onboarding: temp password (CSPRNG, 16+ chars) emailed via `notify.service` after commit; user gets `mustChangePassword: true`. There is no change-password endpoint yet and `authenticate` does not enforce the flag.

**Security & cross-cutting**

- helmet defaults, `x-powered-by` disabled, JSON body limit 1 MB, CORS allow-list (see §3 `app.js`, §6 `CORS_ORIGINS`), no cookies/credentials.
- Rate limiting: `rateLimiter.middleware.js` (see §3). Default 1000 requests / 15 min / IP, in-memory store; effective client IP depends on `TRUST_PROXY` (default `false`, so behind a reverse proxy all clients share the proxy IP until it is configured).
- Logging: pino / pino-http (`logger.js`), redacts authorization header, cookie header and password fields; health routes are not auto-logged; `clientType` logged per request; login failures log only reason, userId and error name/code.
- Error handling: `AppError.js` + `errorHandler.middleware.js` (see §3). Validation errors are `400` with `errors[{field,message}]`; unknown errors are generic `500`.
- Client identification: `clientType.util.js` / `clientType.middleware.js` — informational only.

**Known gaps / TODO**

- Not implemented: a runner for `deleteStaleSessions` (the function and `REFRESH_SESSION_CLEANUP_GRACE_DAYS` exist; nothing calls it, so expired/revoked `RefreshSession` rows still accumulate), change-password, `asyncHandler.util.js`, `duration.util.js`, `config/container.js` (all empty).
- Already issued ACCESS tokens stay valid until they expire (default 15 minutes) after logout, reuse detection or a password reset, because `authenticate` checks the user in the DB but not the session (verified live 2026-10-11 and by `auth.logout.test.js`). Accepted decision (no session id in the access token), not a bug.

**Refresh flow (`POST /api/v1/auth/refresh`, body `{ refreshToken }`):** `refreshLimiter` (own counter) → `validateBody(refreshTokenSchema)` → `refresh` → `refreshTokens`. Unknown token → 401 `INVALID_TOKEN`; revoked token presented (reuse) → `revokeAllByUser` + 401 `INVALID_TOKEN`; expired → 401 `TOKEN_EXPIRED`; user missing → 401 `INVALID_TOKEN`; PENDING/DISABLED → 403; lost race → plain 401 `INVALID_TOKEN` (no revoke-all); success → old session revoked + new one created in one transaction, response `{ success, message: TOKEN_REFRESH_SUCCESS, data: { tokens: { accessToken, accessTokenExpiresIn, refreshToken, refreshTokenExpiresAt } } }`. No audit rows are written for refresh or reuse. The old refresh token stops working immediately; the old ACCESS token stays valid until it expires.

**Deployment note (rate limits):** the login/register limiter (`authLimiter`) is `RATE_LIMIT_MAX` 1000 per `RATE_LIMIT_WINDOW_MS` 15 min per IP (the local `.env` sets neither, so defaults apply); refresh/logout are stricter (60 per 15 min per IP). Counters are per IP and in memory (per process). Behind a reverse proxy or load balancer `TRUST_PROXY` must be set to the number of proxy hops (for example `1`), not `true`, otherwise every user shares the proxy's IP (one shared counter) or a client can spoof `X-Forwarded-For`; default `false`.

**Logout flow (`POST /api/v1/auth/logout`, Bearer access token + body `{ refreshToken }`):** `refreshLimiter` → `authenticate` → `validateBody(refreshTokenSchema)` → `logout` → `logout` service → `revokeSessionWithLogoutAuditTx`. No/invalid/expired access token → 401 (checked before the body), DISABLED/PENDING caller → 403, bad body → 400. For an authenticated caller it is always 200 `LOGOUT_SUCCESS` (`data: null`) whether the token was active, foreign, already revoked, expired or unknown. Only a token that belongs to the caller and is still active is revoked, together with exactly one `LOGOUT` audit row (same transaction); nothing else is touched (other devices keep working, no revoke-all). The access token already issued stays valid until it expires. Password reset (`resetPasswordTx`) separately revokes all of the user's active sessions in the same transaction as the password change.

## 15. Ticket SL-MP-02 — Create a Membership Plan

Implemented `POST /api/v1/plans`:

- **Security & Authorization:** `authenticate` + `authorize(Role.OWNER, Role.ADMIN)`. `Role.COACH` and `Role.MEMBER` receive `403 FORBIDDEN` and create nothing. Unauthenticated requests receive `401 UNAUTHORIZED`.
- **Rate Limiting:** `planLimiter` protects `POST /api/v1/plans` keyed by authenticated `${req.user.id}_${ipKeyGenerator(req.ip)}` (fallback to IP for unauthenticated) and answers `429 TOO_MANY_REQUESTS` on violation. Active in test environment with configurable limit overrides.
- **Validation (422 Unprocessable Entity):** Custom `validateCreatePlan` middleware returns ALL failing issues together with status 422:
  - Required non-negative `price` (supports coercion from string).
  - `creditType === TIME`: `creditsIncluded` must be 0 or omitted (defaulted to 0), `creditRefill` must be null/omitted.
  - `creditType !== TIME`: `creditsIncluded` required whole number $\ge 1$.
  - Recurring `billingCycle` only if `kind === SUBSCRIPTION` with exact message: `"Only a membership renews monthly."`.
  - `creditRefill === MONTHLY` only allowed when `billingCycle === MONTH`.
  - Enforces `status = 'ACTIVE'` and `version = 1`.
  - `externalRef` stripped silently and not persisted.
- **Name Uniqueness & Race Handling:** Pre-check via `findActiveByName` (case-insensitive check against plans where `status != 'ARCHIVED'`). Concurrency race on `membership_plans_name_lower_active_idx` is caught (`P2002`) and mapped to `409` with code `'duplicate_name'`.
- **Transactional Audit Log:** Atomically creates the `MembershipPlan` row and `AuditLog` row (`action: PLAN_CREATED`, `actorId`, `actorRole`, `reason: ${plan.name} (${plan.id})`, `meta`) inside the same Prisma `$transaction`.
- **Derived Fields & Response Format:** Returns `201 Created` with header `Location: /api/v1/plans/{id}` and body `{ success: true, message, data }`. The `data` payload returns numeric `price`, lowercase string enum values, derived `section` (`'online_coaching'` vs `'class_membership'`), `creditSummary` (e.g. `"15 class credits a month"`, `"1 appointment credit"`, `"Time-based access"`), and `activeClientCount: 0`.
- **Web & Mobile Compatibility:** Verified full compatibility for browser (Next.js with Origin) and native mobile (Kotlin without Origin). Bearer authentication and standard JSON bodies.
- **Documentation:** Complete OpenAPI / Swagger 3.1 specification at `/api/v1/docs` under path `/plans`.

## 16. Ticket SL-MP-03 — List and Search Membership Plans

Implemented `GET /api/v1/plans` (see the header and §3 for files).

- **Access and limits:** `authenticate` + `authorize(OWNER, ADMIN, COACH)`; MEMBER → 403, no token → 401. `planReadLimiter` (own counter, same key as `planLimiter`) → 429 `TOO_MANY_REQUESTS`. Order: 401, 403, 429, 422.
- **Query:** `section`, `kind`, `creditType`, `visibility`, `status` (comma list or repeated), `q`, `page`, `pageSize`, `sort`. Enum values are case-insensitive, blank values count as not given. A known param with a bad value → 422 listing every failing field. **Unknown params are stripped (not `.strict()`)** so web and mobile clients can add params; the trade-off (a misspelled name such as `sections=` silently applies no filter) is documented in OpenAPI. Coach and staff schemas stay `.strict()`.
- **Filters:** one `buildListWhere`. Default statuses ACTIVE + INACTIVE; ARCHIVED only when `status` includes it. Section filters on `creditType` (TIME = online_coaching); `section=online_coaching&creditType=class` is an empty 200, not an error. `q` matches name, description and kind label, case-insensitively.
- **Sorting:** `name` (default), `price`, `createdAt`, `-` for descending, `id` as tie-break so paging is stable. The Neon database collation is `C.UTF-8` (case-sensitive: "STRDY" sorts before "Single", "HEROX" before "Hyrox"), so `name` sorts with raw SQL on `LOWER("name")`. The raw query only receives and returns ids (Prisma already filtered), so no WHERE logic is duplicated. A test proves the name path and the column path return the same total and plans for 9 filter sets.
- **`meta.counts`:** `groupBy creditType` on non-archived plans, run in parallel with the list, ignoring `q`, every filter and `status`. Always `{ class_membership, online_coaching }`. Seed: 53 and 7 (plus any non-archived plans created since).
- **Seed facts verified:** 60 plans, all ACTIVE; 7 are TIME (Body Recomposition, HEROX Programme (Female-specific), Hyrox Beginner Program (12 week plan) and (Monthly), Hyrox Personalised Programming, Hyrox Personalised Programming + Nutrition, Nutrition Coaching); `q=nutrition` returns exactly the last two.
- **Performance:** each database round trip is about 200-300 ms from the developer machine to the remote Neon DB, so the endpoint costs: sign-in check (1) + list (1 round trip for `price`/`createdAt`, 2 for `name`). Measured fastest runs for 64 plans: roughly 440-500 ms for `-price` and 700 ms for `name` on that link, i.e. about 100-300 ms of processing beyond the round trips. The list's `findMany` + `count` run in parallel instead of in a `$transaction` (a transaction added about 3 round trips). A hard 300 ms wall-clock assertion against the remote DB is not possible, so the test compares the fastest of 7 runs with 300 ms plus the measured round trip per sequential call. Closer to the database the same code is expected to be well under 300 ms.
- **Open risks:** (1) name ordering cannot use an index and loads every matching plan: fine for a catalogue of tens or hundreds of plans; the later fix is a functional index on `LOWER(name)` (and `pg_trgm` for `q`). (2) `meta.counts` ignoring `status` means the badges include inactive plans. (3) `activeClientCount` is a placeholder (0). (4) The plan list uses `pageSize` + `meta` while the coach list uses `limit` + `pagination`; there is no SL-SV-01 document in the repo, so this inconsistency is unresolved. (5) Validation status codes differ: plans 422, coaches/auth/staff 400.
- **Web and mobile audit (rate limiter):** all endpoints are plain JSON with Bearer auth and `clientType` applies app-wide, so web (Origin) and mobile (no Origin) are both supported everywhere. Endpoints WITHOUT a rate limiter: `GET /auth/me`, `POST /admin/staff`, `POST /admin/staff/coaches`, `GET /coaches`, `GET /coaches/me`, `GET /coaches/:coachId`, `PATCH /coaches/:coachId`, `PATCH /coaches/:coachId/status`, `PATCH /uploads/profile-image`. Public `/health*` are intentionally unlimited.
- **Database change applied:** migration `20261026090000_add_plan_list_index` was applied to the shared Neon dev DB with `prisma migrate deploy`.

## 17. Tickets SL-MP-04 and SL-MP-05 — Get, Update and Change Status of a Membership Plan

Implemented `GET /api/v1/plans/:id`, `PATCH /api/v1/plans/:id` and `PATCH /api/v1/plans/:id/status` (files in the header and §3).

- **Versioning check (requested):** the trigger `bump_membership_plan_version` compares exactly `price`, `billingCycle`, `creditType`, `creditsIncluded`, `creditRefill`, `validityValue`, `validityUnit` = `COMMERCIAL_FIELDS` = the SL-MP-01 list (a test reads the function source and also checks that every table column is classified). Writing a field with its current value (also `100` vs `100.00`) does not bump. The app never bumps the version itself.
- **No-op PATCH:** sending only current values returns 200 with the current plan, without a write, version bump or audit row (assumption, not in the ticket).
- **Existing purchases and price changes:** nothing to enforce yet (no purchases table). Contract for the purchase ticket: a purchase must store the plan `version` it was bought on and billing must read that version, so a price change applies from the next billing cycle; purchase must refuse inactive and archived plans (reads `status`).
- **Gaps and assumptions:** (1) no purchases or clients table: `countActiveClients` is a seam returning 0, `plan_in_use` is proven by a unit test with the seam mocked only; (2) an audit entry has no entity id column, so plan entries are matched through `reason`; (3) the status endpoint writes with a compare-and-set, so two concurrent status changes cannot both succeed (the loser gets `invalid_transition`); a PATCH that loses a race with an archive gets `plan_archived`; (4) Postgres cannot drop enum values, so `down.sql` of the audit migration only drops the column.
- **Report only (not changed, as requested): rate limiter and web + mobile audit of the plan endpoints.** Rate limiter: `POST /plans`, `GET /plans`, `GET /plans/:id`, `PATCH /plans/:id`, `PATCH /plans/:id/status` all have one; the 405 routes have none (they do no work). The earlier list of endpoints WITHOUT a limiter in §16 still stands (auth/me, staff creation, coach routes, profile-image PATCH). Web + mobile: all plan endpoints are Bearer-token JSON with the same envelope and error codes, no cookies, no dependence on `Origin`; tests compare a browser-Origin request with a no-Origin request. Gaps found: (a) CORS has no `exposedHeaders`, so browser code cannot read `Allow` (405), `Location` (201 on create) or the `RateLimit-*` / `Retry-After` headers of a 429 from a cross-origin response; mobile is unaffected; fix later in `app.js` (not touched here); (b) `POST /plans` silently strips `externalRef` and forces `status`, while PATCH rejects them with 422 (intentional per the tickets); (c) validation errors are 422 for plans but 400 for coaches/staff/auth.
- **Open risks:** the 405 handlers answer before authentication (they reveal only that the route exists); the plan name check is a read followed by a write, so the unique index and the P2002 mapping are what finally guard a race; `Json` audit details are not indexed.
